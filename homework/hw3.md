# HW3 (після L05–L06): кеш + інструменти

Мета тижня: система не палить токени на повторні питання і вміє безпечно виконувати дії.

> **Навіщо це в реальній системі.** Кеш — це рішення про коректність, а не про
> швидкість: у мультитенантних системах ключ без тенанта означає, що два
> клієнти з однаковим питанням отримають одну відповідь — це вже витік, а не
> оптимізація. А timeout та ідемпотентність тут не «best practice для галочки»:
> на платформі, яку я супроводжую, ланцюг таймаутів tool-викликів довелося
> редизайнити окремим проєктом, бо рівні розжилися суперечливими лімітами —
> і завислий виклик з'їдав бюджет усього запуску.

## Обов'язково

1. Кеш відповідей: однаковий запит удруге не ходить у модель. Ключ — модель + промпт +
   повідомлення. Рахує hits / misses (знадобиться в HW5).
2. Інструменти: коли модель повертає tool_call (`lookup_order`), виконує його і додає
   результат у відповідь.
3. Фіксує в описі PR два операційні рішення (по 1–2 речення): який timeout на
   tool-виклик і чому; який ключ ідемпотентності для side-effecting дій
   (природний кандидат — `request_id`). Чесна межа, яку варто назвати в описі PR
   (узгоджено з уроком 6): `request_id` закриває лише **твій власний ретрай у межах
   одного запиту**; повторне прохання моделі наступним ходом чи подвійний клік
   користувача — це вже нові `request_id`, і від них захищає лише ключ від самої дії
   (`hash(conversation_id, tool_name, args)`) — він за межами core, але межу назви.
   Поведінкова перевірка ідемпотентності — у HW4, коли з'явиться черга approvals.
   Якщо здача може лишитися без опису PR (перездача, squash, дзеркало без PR) —
   продублюй ці рішення розділом «Операційні рішення» у README: перевірка не
   мусить залежати від платформи.

## Опційно (не оцінюється)

- TTL: кешовані відповіді старіють і перезапитуються.
- Semantic cache: Redis з advanced-профілю + порівняння за схожістю, а не точним збігом.
- Валідація аргументів: tool_call без обов'язкового аргументу → відмова валідації в
  лозі, а не виконання (mock шле порожні `arguments` — кейс симулюється юніт-тестом;
  як завести тест-проєкт у цьому репозиторії — GETTING_STARTED §10).
- Реалізувати timeout на tool-виклик. Чесне застереження: `__delay` затримує
  mock, тобто **виклик моделі**, а не інструмент — tool-таймаут ним не
  перевіряється; перевіряй юніт-тестом (повільного інструмента у стеку немає).

## Що здає

PR, де другий однаковий запит відповідає миттєво (з кешу), а «Де моє замовлення #123?»
повертає відповідь з результатом інструмента.

## Що перевіряє ментор

| Перевірка | Як | Очікується |
|---|---|---|
| Кеш: повтор не пішов у модель | два однакові запити поспіль, потім `SELECT latency_ms, prompt_tokens, completion_tokens, cost_usd FROM requests ORDER BY created_at DESC LIMIT 2;` | у свіжішого рядка `prompt_tokens = 0`, `completion_tokens = 0`, `cost_usd = 0`. Ненульові токени на повторі = кеш не влучає, **незалежно від latency** (на mock «< 50 мс» нічого не доводить: промах теж коштує 9–16 мс) |
| Ключ кешу повний (негативний) | те саме питання (воно вже в кеші) → `POST /prompts/v1/activate` → повторити питання → `SELECT prompt_version, prompt_tokens FROM requests ORDER BY created_at DESC LIMIT 1;` → повернути v2 | мусить бути **промах**: `prompt_tokens > 0` і `prompt_version = v1` — зміна промпта інвалідує кеш, бо промпт сидить у ключі. Відповідь із кешу (0 токенів, стара v2-відповідь) = ключ рахується лише з повідомлення: rollback-механізм тижня 1 мовчки зламаний, а зміна моделі/промпта більше не змінює відповідей = на доопрацювання |
| Лічильники кешу | рев'ю коду (`/chat`) або лог | hit і miss інкрементуються окремо; плитка оживе в HW5 |
| Інструмент | «Де моє замовлення #123?» | відповідь містить **фактичний результат** інструмента (статус замовлення тощо — еталон дописує « (статус: …)»), а не лише намір «перевіряю» без даних |
| Операційні рішення | опис PR (або розділ «Операційні рішення» у README — див. п.3) | timeout і ключ ідемпотентності названі й обґрунтовані |
| Evals | прогін | зелені |

## Самоперевірка перед здачею

Два однакові запити поспіль, потім у БД:
`SELECT latency_ms, prompt_tokens, completion_tokens, cost_usd FROM requests ORDER BY created_at DESC LIMIT 2;` —
у свіжішого рядка токени і `cost_usd` мають бути нульові: повтор не ходив у модель.
Не перевіряй кеш через `latency_ms` < 50 — на mock промах теж вкладається у ці мілісекунди,
і здача зовсім без кешу пройде таку «перевірку».

> Застряг? Еталон тижня можна попросити в ментора: доступ до репозиторію еталонів дається за запитом, після власної спроби.
