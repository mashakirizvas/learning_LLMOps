# HW1 (після L01–L02): логування + prompt registry

Мета тижня: запит проходить крізь систему і лишає слід, а промпт стає версіонованим
артефактом, а не рядком у коді.

> **Навіщо це в реальній системі.** На платформах, де я це бачив, порядок був
> саме такий: спершу заводять контракт метаданих виклику (модель, токени, час,
> статус), і вже поверх нього виростають вартість, метрики й розслідування.
> Команди, які починали з дашбордів, щоразу впиралися в «а давайте спершу
> зберемо дані за місяць». Промпт у реєстрі — з тієї ж родини: він потрібен не
> «для порядку», а щоб у п'ятницю ввечері відкат займав секунди, а не археологію.

## Обов'язково

1. Розбирається, як запит пише рядок у таблицю `requests` (у стартері це вже працює).
2. Наповнює реєстр: у `db/schema.sql` таблиця `prompts` створюється **порожньою** —
   додає seed із двома версіями (`v1` = `You are an assistant.`,
   `v2` = `You are a support assistant. Be concise and helpful.`, активна — `v2`)
   і піднімає базу заново: `docker compose down -v && docker compose up -d`
   (міграція виконується лише на чистому томі — без `-v` зміни в `schema.sql` не застосуються).
3. Переносить system-промпт із хардкоду (`service/Program.cs`, `TODO(student, W1)`) у
   таблицю `prompts`: сервіс бере активну версію. Дефолт на випадок порожнього реєстру —
   **без** слова «support», щоб поломка реєстру була видна, а не замаскована.
4. Пише версію промпта (`prompt_version`) у кожен лог-рядок.
5. Замінює заглушку `GET /prompts` (у стартері вона віддає `{ todo: ... }`, тому картка
   реєстру в консолі показує «—») на список версій і додає `POST /prompts/{version}/activate`
   (promote / rollback). Активація неіснуючої версії має віддавати `404`, а не «тихо»
   знімати активність з усіх.

## Опційно (не оцінюється)

- `finish_reason` у лозі: додати колонку і переконатися, що обрізана відповідь
  (`length`) видно окремо від успішної. Mock віддає `stop` / `tool_calls` — форма
  бойова. Навіщо це в реальній системі — блок 02 уроку 1.
- Audit trail: окрема таблиця активацій — хто, коли, яку версію зробив активною.
- Версія промпта з міткою часу замість перезапису тіла.

## Що здає

PR, де чат працює, промпт живе в БД, консоль показує картку Prompt registry.

## Що перевіряє ментор

| Перевірка | Як | Очікується |
|---|---|---|
| Стек піднімається | `docker compose up --build` | усі контейнери Up, чат відповідає |
| Промпт у БД | `GET /prompts` | список версій, і у відповіді **видно, котра саме активна** (поле `active` чи еквівалент); список версій без ознаки активної — на доопрацювання |
| Реєстр наповнено міграцією | `docker compose down -v && docker compose up --build`, потім `docker compose exec postgres psql -U llmops -d llmops -c "SELECT name, version, active FROM prompts"` | два рядки, active рівно один — **без жодного ручного `INSERT`**: seed справді сидить у міграції `db/schema.sql`, а не в коді сервісу і не вставлений руками. Швидка перевірка джерела: `grep -ri "INSERT INTO prompts" service/` — має дати **нуль** влучань (seed лише в `db/schema.sql`) |
| Активація «сміття» | `POST /prompts/v99/activate` | `404`, активна версія не змінилася |
| Версія в лозі | `POST /prompts/v1/activate` → нове питання в чат → `SELECT model, prompt_version FROM requests ORDER BY created_at DESC LIMIT 3` | `prompt_version` **збігається з активною версією реєстру**: у свіжому рядку лога — `v1`. Непорожність недостатня — константа в лозі цей рядок не проходить |
| Поломка реєстру видна | `docker compose exec postgres psql -U llmops -d llmops -c "UPDATE prompts SET active=false;"` → `POST /chat` | **обидві** умови обов'язкові (перевіряй кожну, «і» — не «або»): відповідь деградує («не знаю» або власний чесний дефолт) **і** `prompt_version` у лозі ≠ версія з реєстру (в еталоні — `none`). Провал будь-якої половини = на доопрацювання: нормальна support-відповідь із `prompt_version=v2` — замаскована поломка; але й нормальна support-відповідь із чесним `none` — теж маскування (дефолт підміняє реєстр непомітно для користувача) |
| Rollback ловиться eval-прогоном | активувати «поганий» промпт → evals; повернути → evals (команда і поріг стартового датасету — `--threshold 5` — GETTING_STARTED §6; цей самий поріг чинний для прогонів у hw1–hw4, поки датасет стартовий) | прогін на v1 — результат **нижче порога** (exit 1; на стартовому датасеті еталонна картина — 3/6), на v2 — зелені. «Один-два червоні кейси при зеленому підсумку» — це не «ловиться» |

## Самоперевірка перед здачею

Активуй промпт без слова «support» → mock відповідає «не знаю», evals червоніють.
Поверни хороший → зелені. Відтворюється — registry зроблений правильно.

> Evals поки що використовуємо як **чорну скриньку**: готовий runner уже лежить у
> `evals/`, команда запуску — GETTING_STARTED §6. Як він влаштований усередині —
> урок 10; гейтом у CI він стане на тижні 6.
