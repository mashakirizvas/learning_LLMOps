# HW2 (після L03–L04): routing + cost

Мета тижня: система сама обирає модель під задачу і знає, скільки коштує кожен запит.

> **Навіщо це в реальній системі.** Найбільший важіль вартості — не «дієта»
> промпта, а те, що дороге дістається лише складному: різниця між дешевою і
> сильною моделлю — порядок, а не відсотки. І маршрутизувати треба не лише
> запити користувачів: на одній агентній платформі найжирнішим споживачем
> виявився службовий LLM-виклик усередині кожного запуску — його свідомо
> перевели на дешеву модель без утрати якості. Прайс при цьому — живі дані:
> ми ловили в каталозі ціни, що вже розійшлися з тарифами постачальника, і
> виправляли їх як баги.

## Обов'язково

1. Routing: обирає модель за задачею. Мінімум два маршрути: звичайні питання →
   `mock-mini`, повернення/скарги/термінове → `mock-strong` (обидві вже описані в
   `gateway/litellm-config.yaml`).
2. Cost: заводить табличку цін за 1k токенів, рахує вартість кожного запиту і пише
   в `cost_usd`.
3. Реалізує `GET /cost` → `{ today_usd, budget_usd }` — консоль покаже
   «Вартість сьогодні».
4. Фіксує fallback-порядок як політику: рядок-константа/коментар біля роутера
   («хто підхопить, якщо основна впала») — механізм оживе в HW4.

## Опційно (не оцінюється)

- Budget-політика: при 80% бюджету — алерт у лог або деградація на дешевшу модель.
- Третій маршрут (окремий tier для FAQ, ескалацій і «всього іншого»).

## Що здає

PR, де в таблиці `requests` різні моделі для різних питань і заповнений `cost_usd`;
плитка вартості в консолі жива.

## Що перевіряє ментор

| Перевірка | Як | Очікується |
|---|---|---|
| Routing працює | звичайне питання (наприклад, англійське «How do I reset my password?») **плюс** українська ескалація «поверніть гроші терміново» (кирилицю в Git Bash шли з файлу: `--data @file.json`, інакше маркери не спрацюють), потім `SELECT model, count(*) FROM requests GROUP BY model` | дві різні моделі. Перевіряються **обидві мови**: роутинг на ключових словах однієї мови — половина роутера |
| Cost рахується | `SELECT cost_usd FROM requests WHERE cost_usd > 0 LIMIT 3` | є значення (фільтр `> 0` — бо нульова вартість легальна: з тижня 3 її даватиме cache-hit) |
| Ціна залежить від моделі | `SELECT DISTINCT model, round(cost_usd/(prompt_tokens+completion_tokens), 9) AS unit FROM requests WHERE cost_usd > 0;` | питома ціна `mock-strong` вища за `mock-mini` **на порядок** (в еталоні ~16×) — бо ціни беруться з таблички за моделлю. Однакова питома ціна, або різниця лише в десятки відсотків, = пласка ставка замість таблички цін = на доопрацювання |
| Fallback-порядок | код біля роутера | у **коді** біля роутера — рядок-константа або коментар із повним порядком (напр. `// fallback chain: mock-strong -> mock-mini -> заглушка`), який на тижні 4 стане кодом; опис у PR — додатково, не замість |
| Консоль | плитка «Вартість сьогодні» + `GET /cost` | готова консоль округлює до центів, тож на mock плитка чесно показує `$0.00` — це очікувано; критерій перевіряється через `GET /cost` (`today_usd > 0`), а не через число на плитці |
| Ендпоінт не бреше (негативний) | `GET /cost` → одразу `SELECT round(SUM(cost_usd), 4) FROM requests WHERE created_at::date = CURRENT_DATE` | `today_usd` **збігається** із сумою в БД (допуск — запити, зроблені між двома командами). Розбіжність у рази = ендпоінт віддає константу «щоб плитка ожила» = на доопрацювання: `today_usd > 0` сам по собі чесність не доводить |
| Evals | прогін | зелені |
