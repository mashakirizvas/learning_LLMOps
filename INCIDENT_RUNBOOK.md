# INCIDENT RUNBOOK

Операційний сценарій для капстон-системи (LLM control plane). Кожен інцидент —
чотири кроки: **Симптом → Підтвердження → Дія → Перевірка відновлення**.

> **Порти.** Команди нижче використовують стандартний порт `8080` (саме так
> піднімається свіжий клон). Якщо `8080` зайнятий і ви запускаєте стек зі
> зсувом портів (`docker-compose.override.yml`), підставте свій порт — напр.
> `18080`. Це задокументована підстановка, а не відхилення від «дослівності».

---

## Інцидент 1: провайдер недоступний (5xx / таймаути)

| Крок | Що саме |
|---|---|
| **Симптом** | Користувачі повідомляють, що «бот вибачається» замість відповіді по суті. Зростає частка помилок. |
| **Підтвердження** | У `/observability` зростають `fallback_events` і `error_rate_pct`; у лозі сервісу зʼявляються статуси `503`. |
| **Дія** | Втручання не потрібне: fallback і контрольована деградація вже працюють. Користувач отримує ввічливу заглушку, сервіс не падає. Спостерігати, доки `error_rate_pct` не спаде. |
| **Перевірка відновлення** | **Нове** запитання (не з кешу) знову отримує відповідь по суті; `error_rate_pct` спадає. `fallback_events` — кумулятивний лічильник, він не спадає, тож дивимось саме на error rate. |

### Відтворення (дослівно)

Маркер `__fail_503` у тексті повідомлення змушує mock-провайдера повертати 503 —
так інцидент відтворюється без реального збою.

**0. Чистий старт** (щоб кілька збоїв було видно на тлі порожнього лога):

```sh
docker compose down -v
docker compose up -d --build
```

Зачекайте ~30 с на готовність gateway (холодний LiteLLM 500-ить перший запит).

**1. Нормальна робота** — звичайна відповідь:

```sh
curl -s localhost:8080/chat -X POST -H "Content-Type: application/json" \
  -d '{"message":"Як скинути пароль?"}'
```

**2. Початок інциденту** — два повідомлення з маркером збою:

```sh
curl -s localhost:8080/chat -X POST -H "Content-Type: application/json" \
  -d '{"message":"__fail_503"}'
curl -s localhost:8080/chat -X POST -H "Content-Type: application/json" \
  -d '{"message":"__fail_503"}'
```

Кожне повертає ввічливу заглушку («Вибачте, тимчасові проблеми…»), **не** 500.

**3. Підтвердження** — метрики консолі:

```sh
curl -s localhost:8080/observability | python3 -m json.tool
```

Очікувано: `fallback_events` > 0, `error_rate_pct` > 0, у `errors` зростає
`provider_503`.

**4. Перевірка відновлення** — **нове**, не кешоване запитання:

```sh
curl -s localhost:8080/chat -X POST -H "Content-Type: application/json" \
  -d '{"message":"Що ти можеш?"}'
```

Відповідь по суті = провайдер відповідає знову. Контрольне питання тут **нове**
навмисно: запитання з кроку 1 уже в кеші й віддало б `latency_ms=0` навіть під
час збою, створивши хибне враження відновлення.

**5. Очищення кешу** — якщо під час збою в кеш могли потрапити заглушки
(в цій реалізації не кешуються — пишемо лише 2xx без tool), очищення кешу = рестарт:

```sh
docker compose restart service
```

### Хронологія навчального інциденту

| Час | Подія | Що відбувається |
|---|---|---|
| 10:00 | Нормальна робота | «Як скинути пароль?» → звичайна відповідь. |
| 10:02 | Початок інциденту | `__fail_503` → ввічлива заглушка замість 500; `fallback_events` і error rate зростають. |
| 10:05 | Перевірка метрик | `/observability` підтверджує сплеск fallback і помилок. |
| 10:08 | Відновлення | Нове запитання → відповідь по суті; `fallback_events` більше не зростає. |

**Що зробимо, щоб не повторилося?** Додати до `/observability` алерт на
`error_rate_pct` понад поріг за вікно часу (напр. >5% за 15 хв), щоб інцидент
було видно за метриками консолі ще до скарг користувачів.

**Як ми дізналися про інцидент?** У навчальному сценарії — зі скарг. Правильний
стан: такий інцидент має бути помітний за консоллю (сплеск `fallback_events`,
зростання error rate) раніше за скарги. Це й закриває попередній пункт.

## Інцидент 2: деградація якості (HTTP-метрики в нормі)

| Крок | Що саме |
|---|---|
| **Симптом** | Скарги на некоректні відповіді, хоча HTTP-метрики (error rate, p95) в нормі. |
| **Підтвердження** | Перевірити `prompt_version` в останніх записах лога: чи збігається зростання скарг з активацією нової версії промпта? Чи ловить локальний прогін evals проблему? |
| **Дія** | Відкотити промпт на попередню версію однією командою. |
| **Перевірка відновлення** | evals проходять; скарги зменшуються. |

### Відтворення (дослівно)

**Відкат версії промпта** (rollback за секунди, без деплою):

```sh
curl -s localhost:8080/prompts/v1/activate -X POST -H "X-Actor: oncall"
```

Підставте замість `v1` цільову (попередню) версію. Перевірка активної версії:

```sh
curl -s localhost:8080/prompts | python3 -m json.tool
```

Після відкату — прогнати evals локально й переконатися, що поріг знову береться:

```sh
docker run --rm --network my-bootcamp_default \
  -e SERVICE_URL=http://service:8080 -e PYTHONUTF8=1 \
  -v "$(pwd)/evals:/e:ro" python:3.12-slim \
  python /e/run.py --dataset /e/golden.jsonl --threshold 9
```

## Критерії відкату (пишуться ДО релізу)

```
Відкочуємо, якщо:
  eval pass rate < 9/10          (прогін після деплою)
  АБО fallback_events зростає    протягом 15 хв
  АБО error_rate_pct > 5%        протягом 15 хв
Хто: черговий, без погоджень.
Як: POST /prompts/{попередня}/activate — одна команда.
```
