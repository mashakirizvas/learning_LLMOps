# Starter repository

Те, що студент клонує на першому уроці й дороблює до capstone.

**➡ Повний гайд для студента (вимоги, запуск, кожна папка, troubleshooting): [GETTING_STARTED.md](GETTING_STARTED.md).**
**➡ Домашні завдання — окремий файл на кожен тиждень: [homework/](homework/README.md).**

## Що дається готовим, що добудовує студент

| Компонент | Дається готовим | Студент добудовує |
|---|---|---|
| UI (Angular) | готові в'юхи: Chat + Console/Observability | не змінює |
| App service (.NET) | skeleton | control plane: routing, fallback, cost, policies |
| Observability API (.NET) | skeleton | агрегати з Postgres (traces, p95, cost, error-taxonomy) у Console-в'юху |
| Gateway (LiteLLM) | базовий конфіг | моделі/провайдери, порядок fallback |
| Mock provider | готовий | використовує для тестів і failure-сценаріїв |
| Postgres | базова схема | розширює під logs / cost / prompt records |
| Eval runner (Python) | skeleton | dataset, graders, пороги |
| CI (GitHub Actions) | шаблон `.github/workflows/eval-gate.yml` | eval gate |
| Redis / дашборди | опційний шаблон | advanced extension |

## Запуск (мінімальний стек)

```sh
docker compose up --build
```

Піднімаються: UI (`:4200`), сервіс (`:8080`), LiteLLM (`:4000`), Postgres, mock provider.
Для mock реальні ключі не потрібні. Redis і дашборди — опційні: `docker compose --profile advanced up`.
Для оцінки якості (model-based evals): `cp gateway/.env.example gateway/.env` і заповнити ключі.


## Операційні рішення (W3)

**Timeout на tool-виклик.** Визначено per-tool у реєстрі (`ToolSpec.TimeoutMs`, зараз 2000 мс) і застосовано в коді: виконання інструмента обгорнуте в `WaitAsync(TimeoutMs)` з `catch (TimeoutException)` → завислий інструмент дає оброблену помилку, а не вішає весь запит і не палить бюджет. У стеку немає повільного інструмента (mock повертає миттєво), тому таймаут не спрацьовує наживо — механізм правильний, але демонструється лише на реальному повільному інструменті (W4). Юніт-тесту на нього поки немає.

**Ключ ідемпотентності.** Природний кандидат для core — `request_id` (закриває власний ретрай у межах одного запиту). Межа: повторне прохання моделі наступним ходом або подвійний клік — це вже нові `request_id`; від них захищає ключ від самої дії `hash(conversation_id, tool_name, args)` (щоб два однакові `create_ticket` дали один тікет). Цей ключ поза core; поведінкова перевірка — у W4.

## Семантичний кеш (опційний, advanced)

Другий ешелон кеша **після** точного хеша: точний збіг → промах → embedding запиту (через gateway) → пошук найближчого в Redis за косинусною схожістю → якщо score ≥ поріг, віддаємо кешовану відповідь, інакше йдемо в модель. Ловить переформулювання того самого питання, які точний хеш пропускає ("скинути пароль" vs "забув пароль").

**Порядок свідомий:** embedding коштує час і гроші, тому семантична перевірка стоїть за безкоштовним точним хешем, не перед ним.

**Налаштування (env):**
- `SEMANTIC_THRESHOLD` — поріг косинусної схожості (дефолт `0.85`, консервативний: для support-бота ціна хибного хіта вища за зайвий виклик моделі).
- `EMBEDDING_MODEL` — модель embedding (дефолт `text-embedding-3-small`).

**Вмикання:** потрібен Redis (`docker compose --profile advanced up`) і реальний ключ OpenAI у `gateway/.env` (embedding не працює на mock — потрібна справжня модель).

**Модель у ключі/записі:** і точний, і семантичний кеш враховують модель (точний — у хеші ключа, семантичний — окремим полем у записі Redis + фільтр при пошуку), щоб fallback-відповідь не перевикористовувалась для основної моделі.

**Відоме обмеження:** пошук — лінійний скан `semcache:*` (прийнятно для демо; у проді — векторний індекс redis-stack / HNSW).

## Evals: golden dataset і поріг (W5)

`evals/golden.jsonl` — контракт поведінки бота: 10 кейсів (6 стартових + 4 власних: greet-1, thanks-1, safety-2, order-2). Серед власних ≥2 негативні (`safety-2` з `expect_refusal`, `order-2` з `forbid`).

**Поріг: 9 з 10** (правило N−1). Чому N−1: допускає падіння рівно одного кейса — толерантність до поодинокого флейку на реальній моделі, — але будь-яка справжня регресія (напр. відкат промпта v2→v1) валить ≥2 кейси й опускає прогін нижче порога. Поріг має оновлюватись разом із розміром набору і в локальному запуску, і в `.github/workflows/eval-gate.yml`.

**Перевірка на фальш-позитиви:** копія датасету з префіксом `__fail_503` у кожному input має давати 0 пройдених — кейс, що зеленіє під повним збоєм, нічого не перевіряє. Позитивні кейси мають `forbid` із фрагментом заглушки деградації («тимчасові проблеми»), інакше вони фальш-позитивні під збоєм (напр. `thanks-1`: заглушка теж містить «будь ласка»). Injection-детекту на вході немає (свідомо, з W4), тож `expect_refusal`-кейси під збоєм теж падають — винятку не потрібно.

## SLO і бюджет помилок (W5 опційно)

**SLI** (що міряємо): частка звернень зі змістовною відповіддю — без переходу в заглушку деградації. У логу це частка рядків зі `status = 200`.

**SLO** (ціль): не менше 99% звернень за тиждень отримують змістовну відповідь. Орієнтир на користувача, не на uptime: доступний сервіс, що віддає лише заглушки, формально живий, але корисної відповіді не дав.

**Бюджет помилок:** 1% від тижневого обсягу. За ~1000 звернень/тиждень це 10 невдач. Поки бюджет не вичерпано — можна котити зміни; вичерпався — пріоритет на стабільність.

**Таксономія помилок** (`/observability` → `errors`): лічильники `provider_429`, `provider_503`, `db_error` зростають на mock реально; `tool_timeout`, `guardrail_refusal` — завжди 0 (exec миттєвий, refusal дає провайдер), чесно позначені. Лічильники в пам'яті, обнуляються при рестарті.
